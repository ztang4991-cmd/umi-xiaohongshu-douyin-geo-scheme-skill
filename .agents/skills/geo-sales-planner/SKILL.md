# GEO 销售方案工作流

## 1. 先判断任务

把请求归入以下一种或多种类型：快速判断、诊断复盘、标准方案、深度提案、内容生产、销售支持、调研核验、文档制作或自动化开发。只要任务会影响客户的商业目标、预算、资源取舍、合作决策或销售转化，就按销售方案任务处理。

先读取当前项目中的相关资料、已有方案、数据、脚本、输出物和授权边界。搜索优先使用 rg 或 rg --files。如果项目包含团队案例素材库，先读取其 README.md，再选择与方案主题匹配的图片；素材缺失时不要虚构内容，明确说明限制。需要在对外方案中介绍团队、项目案例或合作方向时，读取 references/team-profile.md。

## 2. 方案前置引导式问答

销售方案、合作提案、运营策略、诊断转方案和复杂销售支持必须先问清楚，再研究和写方案。即使用户已经给出完整简报，也至少复述当前理解并确认一个关键变量。

执行以下协议：

1. 每轮只问一个问题，不发送整套问卷。
2. 每次提问前，用一句话说明上一条回答让当前理解发生了什么变化。
3. 区分事实、解释、价值判断、目标、约束和假设；发现把愿望当事实时直接标注。
4. 只问可能改变目标、策略、预算、资源、合规或交付形式的问题。
5. 主问题最多 6 个，通常 3-6 个；信息足够就停止。
6. 按优先级确认：商业结果、目标客户与决策人、当前瓶颈与证据、优势与证明、预算/资源/时间/授权、交付物与审批场景。
7. 将“增长、转化、效果、精准客户”等词转换成可观察的定义、时间范围和指标口径。
8. 结束时输出需求确认单：原始请求、真实问题、已确认事实、未验证假设、关键变量、当前主问题、交付物与验收标准、下一步确认项。
9. 如果主问题或方案方向发生变化，先请销售确认需求确认单，再进入完整方案；方向未变且销售明确授权继续时，可直接推进。
10. 非方案类的低风险任务可以用快速引导模式，最多 3 个问题；不要把简单改写扩展成完整访谈。

第一轮可从以下问题中选最能改变结论的一项，而不是机械按顺序询问：

- 这次方案最终要推动客户做出什么商业决定或行动？
- 目标客户是谁，谁是实际决策人，决策发生在什么场景？
- 当前最明显的瓶颈发生在“被看见、被理解、被信任、被咨询、被转化、被复购/推荐”的哪一段？有什么原始证据？
- 现在认为的优势、差异化或案例证明，哪些已有资料支持，哪些只是销售判断？
- 预算、团队、时间、账号权限、素材授权和线下承接能力有哪些硬约束？
- 方案要给谁在什么会议或审批场景使用，怎样算可用？

## 3. 选择思考方法

完成需求确认后，只选择真正有助于当前判断的方法，不机械堆叠：

- 用双层解释同时服务决策者和执行团队：先给通俗结论，再给机制、边界、证据和误区。
- 用反向拆解分析优秀方案、竞品账号、内容、流程或历史交付物，提炼可迁移规律和操作清单。
- 用横纵分析研究市场、品牌、账号或竞品：纵向看起源、转折、路径依赖；横向用统一维度比较对象。
- 用事实核查拆分事实、推论和价值判断，检查来源、时间、样本、上下文、因果关系和反向解释。
- 用专家会诊组织 3 个互补视角，互相质疑共同事实、分歧与背后假设，再输出适用条件、最大风险、退出条件和第一步行动。
- 用第一性原理区分基本事实、未验证假设、真实目标和现实约束，检查方案是否只是在修补表面。
- 用跨领域借解抽象问题底层结构，比较至少 3 个距离较远领域的解决机制，并写清迁移条件和失效条件。
- 用双向钢人论证公平比较两个选项的最强理由、收益、风险、适用条件和反对意见，找出关键变量。
- 用最小实验替代无休止讨论：围绕最可能改变结论的假设，设计低成本、可逆、有周期、有指标和停止条件的测试。

完整方法卡片见 references/methods.md；需求确认单模板见 references/intake-template.md；团队背景、正式案例和合作口径见 references/team-profile.md。

## 4. 形成方案

按以下顺序推进，按任务删减：

1. 明确主商业目标，避免曝光、涨粉、互动、线索和成交全部成为第一目标。
2. 建立证据底座，标注事实、推断、建议和待确认项；需要最新信息时重新核验并记录来源日期。
3. 诊断漏斗瓶颈：被看见 -> 被理解 -> 被信任 -> 被咨询 -> 被转化 -> 被复购/推荐。
4. 用一句话写出策略主张：对谁、在什么场景、用什么证据、通过什么机制推动什么行为、改善什么结果。
5. 拆成负责人、时间、资源、产出、指标、继续/调整/停止条件。
6. 对高不确定事项优先安排最小实验，而不是直接承诺长期投入。
7. 先完成 Markdown 源稿，再按需要生成 DOCX、PDF、PPT 或表格，并做结构、字体、分页、表格溢出和中文显示检查。

正式方案通常包括：执行摘要、现状与诊断、目标客户与决策路径、策略主张、GEO 与内容系统、平台执行、排期与资源、预算情景、KPI 与复盘、风险与前置条件、下一步行动。不要为了完整而机械添加 SWOT、4P 或用户画像。

## 6. 交付前检查

交付前确认：

- 已完成前置引导并保留需求确认单；
- 主目标、目标客户、决策链、转化入口和优先级清楚；
- 事实、假设、推断、建议和待确认项分开；
- 关键判断有数据、来源或验证计划；
- 动作有负责人、时间、资源、产出和指标；
- 预算、授权、合规、销售响应和线下承接限制已说明；
- 没有保证排名、流量、成交或 ROI；
- 案例和图片使用符合授权与隐私边界；
- 需要生成文件时已完成必要的渲染或预览检查；
- 结尾包含客户确认事项、立即可执行的 3-5 个动作、首次复盘要求和剩余风险。

## 7. 默认提案结构

正式合作提案（面谈版 PDF 或 Markdown 源稿）通常按以下节序组织，可按任务删减但不得随意调换节序，以保证不同项目的提案可以被销售快速熟悉和复用：

| 节序 | 节名 | 核心问题 | 必填 |
| --- | --- | --- | :---: |
| 01 | 合作建议 / 执行摘要 | 建议做什么、周期多长、验收标准是什么 | ✓ |
| 02 | 账号 / 线上现状诊断 | 当前主页传达了什么、还缺什么订购/决策信息 | ✓ |
| 03 | 竞对分布 | 周边同类商家在哪、用什么口径初筛（附竞对口径说明） | ✓ |
| 04 | 竞对线上动作 | 对手在小红书/抖音/OTA 做了什么、远山/该客户怎么应对 | ✓ |
| 05 | 目标客群与决策路径 | 按出行目的/宴会类型分群、每群订房/看场时想解决什么 | ✓ |
| 06 | 平台搜索布局 | 覆盖哪五类搜索意图、账号怎么搭 | ✓ |
| 07 | 内容计划（三阶段节奏） | 三阶段各做什么、每周/每月产量、每阶段测什么 | ✓ |
| 08 | 双方分工 | 运营团队 vs 客户 / 门店各负责什么、时间节点 | ✓ |
| 09 | 效果衡量（四段漏斗） | 三个节点各看什么数、定什么决策 | ✓ |
| 10 | 合作档位 / 报价框架 | A/B/C 档差别在哪、不含什么、主要风险 | ✓ |
| 11 | 团队案例 | 正式案例图片 + 口径说明 | 按项目定 |
| 12 | 面谈确认项 | 启动前必须由客户确认的清单 | ✓ |

**使用要点**

- 生成 PDF 前先完成 Markdown 源稿，章节编号和标题与上表保持一致，便于后续 `build_proposal.py` 定位章节。
- 报价数字不写进 Markdown 源稿，面谈时口头或单独出报价单；提案里只写档位差异和费用组成项。
- 三阶段节奏（方法卡）和四段漏斗（方法卡）是第 07 节和第 09 节的直接输入，直接从 references/methods.md 调取口径，不重新发明定义。
- 竞对口径说明固定引用 references/methods.md "竞对初筛口径"的标准表述，不在每份提案里重写。

## 8. 共享与便携性

本技能只依赖技能目录、当前项目资料和用户提供的原始材料，不依赖个人绝对路径、私有账号或未说明的后台权限。分享给团队时，整体复制 geo-sales-planner/ 目录；若团队没有项目案例素材库，技能仍可运行，只需将案例模块标记为待补素材。
